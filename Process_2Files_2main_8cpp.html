Files – the XenevaOS file manager

Widget tree. Every rectangle below is computed by a Chitralekha BorderLayout; nothing in this file hard-codes a widget position:

rootLayout client area (window minus the titlebar) |- TOP ChMenubar - CENTER mainLayout |- TOP FilesToolbar sidebar toggle | back fwd | up | breadcrumb | refresh | search |- BOTTOM FilesStatusBar item counts / selection / sort order - CENTER bodyLayout (1px hgap = hairline divider) |- LEFT ChSidebar Favourites + Locations (partitions) `- CENTER ListView Name | Date Modified | Size | Kind

The layouts are pure geometry managers. They are NOT added to the window's widget list; the leaf widgets are. That keeps the window's own hover/leave dispatch (ChWindowHandleMouse) working for every leaf, which matters for the Sidebar: it only clears its hover row when it receives the "leave" event.

Memory policy

  • one directory cache (FilesEntry, 44 bytes/entry) reused across folders, grown by doubling and trimmed when a much smaller folder is opened
  • one int block holding the sort order, the filtered view and the merge sort scratch area (no allocation per sort / per keystroke)
  • ListView item storage is reserved up front and trimmed the same way
  • paths and history are fixed buffers: navigation never touches the heap
  • everything the app allocates is released in FilesOnClose / ChDestroy

Complexity

  • sort: stable bottom-up merge sort, O(n log n) worst case, O(n) when the order is already sorted, no recursion (the XEClib qsort is a Lomuto quicksort: O(n^2) and n-deep recursion on sorted input)
  • type-to-select: O(log n) binary search while sorted by name
  • relayout on resize: O(1); repaint only touches dirty regions */
