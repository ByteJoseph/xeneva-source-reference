284/*
285 * UART_ICR is a genuine two-meanings collision, and it is order-dependent.
286 *
287 * mainline's value here (0x05) is the 16550's index-control register in
288 * special mode. BaseHdr/Drivers/uart.h defines the *same* name as 0x44 --
289 * PL011's interrupt-clear register -- because that header is the register set
290 * Xeneva's own PL011 console driver speaks, and <linux/printk.h> includes it
291 * (for UARTDebugOut). So a translation unit that sees both gets whichever
292 * came last, and this is not hypothetical: 8250_port.c includes printk.h at
293 * the top (through module.h) and <linux/serial.h> -> this header at line 28,
294 * so the 16550 value wins there, which is the correct one for it.
295 *
296 * Every other shared name (UART_DR, UART_FR, UART_LCR, ...) happens to have
297 * the same value on both, which is why only this one warns -- and why the
298 * hazard is easy to miss. A future include that pulled Drivers/uart.h in
299 * *after* this header would silently hand 8250 a PL011 register number, and
300 * the symptom would be a port that builds, probes and then never answers,
301 * with no diagnostic at all.
302 *
303 * Nothing is being renamed to fix it: Drivers/uart.h is Xeneva's own header
304 * and this one is mainline's, so neither side may be edited to suit the other.
305 * The protection is this note plus the include order above. Recorded as an
306 * open hazard in DCL_TODO.md.
307 */
308#define UART_ICR 0x05 /* Index Control Register */
