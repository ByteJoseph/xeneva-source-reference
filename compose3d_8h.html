DeodhaiXR 3D compositor (software).

World model – the camera sits at the origin and can only rotate:

  • yaw : true 3D rotation about the vertical axis
  • pitch : y-shearing (the screen image slides vertically), which keeps every window a planar, perspective-correct quad and keeps the panorama lookup a pure table walk World units are window pixels: a window at a depth equal to the focal length (screen width / 2 at the 90 degree field of view) facing the camera appears exactly 1:1, which is where every window is placed when 3D mode is switched on (so nothing jumps).

Layers, back to front:

  1. panorama – a cylindrical wallpaper rendered into the back surface (DeoGetBackSurface), so every existing restore path (DeodhaiBackSurfaceUpdate, alpha HUD blends, the glass blur bake) keeps working unchanged
  2. normal windows – textured quads, painter-sorted by depth; popups ride on their parent's plane
  3. HUD – always-on-top windows (dock, launcher, systray) stay screen-locked and go through the existing 2D composers
  4. cursor

Zoomed windows are screen-locked by definition: while one is visible the frame is delegated to XRComposeFrame unchanged.

Cost per frame (N windows, R repaint regions):

  • bookkeeping : O(N) – hash lookup by Window*, insertion sort on a nearly sorted list, one sync per frame
  • idle / client damage : O(damaged screen area x overlapping windows), same shape as the 2D dirty path
  • window moved/eased : O(old + new projected area)
  • camera moved : O(screen pixels) for the panorama: per column work hoisted to an O(W) table each frame, four columns per NEON step, 2x2 blocks while dragging
  • window pixels : O(projected area), exact per-scanline spans; 1:1 rows blend straight from the source with NEON, perspective rows sample exactly every <=16 pixels (error < 1/4 texel) and step in fixed point, then blend with NEON
