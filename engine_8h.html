Runs on its own thread (AcAudioThread). It owns the sound device, the open file and every decode buffer; the UI talks to it only through AcShared, a small block of lock-free fields:

UI -> engine : cmdSeq/cmd/path (handshake: the UI writes a new path only after ackSeq caught up), paused, seekPermille, quit engine -> UI : state, position, duration, format, end-of-track sequence, and a ring of the most recent output samples (visualizer)

Why the engine never waits for the UI:

  • nothing here takes a lock; the visualizer ring is overwritten blindly and the UI tolerates a torn read (it is only drawn, never played)
  • every decode buffer is static: no malloc on the audio path

Why the UI never starves the engine:

  • virtio-snd's write spins in the kernel with IRQs masked until the host has consumed the block, so writes pace playback by themselves. The engine yields for AC_YIELD_MS right after each write: that window is where the UI thread (and the compositor) get the CPU. The UI keeps each frame short, and the 1 ms scheduler tick preempts it if it overruns.

File I/O contract (FAT driver): a read always consumes whole clusters and a seek lands on a cluster, so this reader only ever reads 4096-byte blocks from 4096-aligned offsets and does any byte skipping itself.
